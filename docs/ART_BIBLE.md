# As Above, Roll Below — Art Bible

**Status:** C-stage active canon  
**Purpose:** make every generated, drawn, animated, and implemented visual asset look as though it belongs to the same unusually expensive game.

---

# 1. VISUAL THESIS

**A serious late-1990s dark-fantasy sourcebook was found inside an evidence archive, then rebuilt as a modern premium game interface by people who have stopped distinguishing occult diagrams, monster ecology, and field documentation.**

The game should combine:

- polished modern 2D game readability;
- high-craft fantasy / weird-fiction illustration;
- engraved and manuscript-like precision in secondary graphics;
- restrained photocopy / archive contamination;
- field-manual diagrams and marginal notation;
- tactile dice;
- mundane institutional detail treated with the same dignity as impossible creatures.

The game must **not** visually imitate Munchkin's doodle/cartoon language.

It also must not become:

- generic `black background + gold occult sigil` design;
- faux-SCP containment-file UI;
- retro pixel art merely because the game is indie;
- muddy painterly fantasy where mechanics disappear into atmosphere;
- AI-art collage with a different style for every enemy.

---

# 2. CORE ART PRINCIPLE

## THE JOKE GETS PREMIUM PRODUCTION

Ridiculous subject matter does not receive deliberately bad artwork by default.

The contrast is part of the identity:

- the monster may be absurd;
- its anatomy is still designed;
- the lighting is still intentional;
- the material rendering is still excellent;
- the UI still gives it the dignity of a final exam.

Bad drawing may be used **inside the fiction** when a sourced object is actually crude, amateur, photocopied, hand-drawn, or badly reproduced. It is never the default excuse for cheap production.

---

# 3. VISUAL INGREDIENTS — USE / DO NOT COPY

Reference families inform principles, not literal style transfer.

## A. EARLY-MODERN DIAGRAMMATIC PRECISION

Use:
- circular and tabular construction;
- dense letter/number systems;
- measured geometry;
- hand-recorded diagrams whose seriousness exceeds immediate comprehension.

Research examples include John Dee manuscript material and early alchemical/esoteric diagrams.

Do not:
- paste historical seals across every interface;
- reproduce a protected modern redraw;
- treat one diagram as a universal occult alphabet.

## B. 1990s RPG SOURCEBOOK AUTHORITY

Use:
- strong creature silhouettes;
- full-page bestiary dignity;
- practical callouts;
- illustrations that feel like someone studied the anatomy;
- occasional black-and-white/limited-value inset art.

Do not:
- imitate the layout, line, or character design of a specific commercial RPG property.

## C. ARCHIVE / FIELD MATERIAL

Use:
- accession marks;
- index tabs;
- crop marks;
- typewritten or monospaced metadata in small doses;
- physical paper wear only when it carries hierarchy or history;
- diagram arrows and specimen callouts.

Do not:
- cover every panel in coffee stains, redactions, paperclips, and `TOP SECRET` stamps;
- let faux documents replace game UI clarity.

## D. MODERN PREMIUM GAME UI

Use:
- generous negative space;
- precise alignment;
- high-contrast information hierarchy;
- immediate combat arithmetic;
- fast motion;
- crisp iconography;
- responsive composition.

The player should never have to admire the art before understanding the roll.

---

# 4. RENDERING LANGUAGE

## Primary illustration style

**Painterly-ink hybrid.**

Characters and monsters should look hand-illustrated rather than photoreal and rather than cel-shaded.

Target qualities:

- confident contour hierarchy, but not a uniform comic-book outline;
- controlled edge variation: sharp around gameplay silhouette / focal anatomy, lost or textured in secondary surfaces;
- brush-textured value masses;
- selective hatching / engraved micro-detail in materials and callout art;
- believable anatomy even when anatomy is impossible;
- high material specificity: old leather is not `brown`, oxidized brass is not `yellow`, painted fiberglass is not biological skin;
- faces and eyes readable at combat scale without becoming portrait photography.

## Detail hierarchy

At runtime distance, the player reads in this order:

1. silhouette;
2. face/head/focal anomaly;
3. weapon or rule-bearing anatomy;
4. large material blocks;
5. research/deep-cut details;
6. microtexture.

If level 5 destroys level 1, the asset fails.

---

# 5. VALUE STRUCTURE

The game should remain readable in grayscale.

### Characters / enemies
- strong separation between subject and environment;
- one dominant dark/light mass;
- one secondary internal mass;
- small high-contrast focal accents.

### UI
- combat values and dice states must reach accessibility contrast targets independently of decorative texture;
- decorative line art is never allowed to compete with numbers.

### Environment
- background value contrast stays lower than active combatants;
- high-detail zones should frame, not sit directly behind, dice and damage previews.

---

# 6. COLOR SYSTEM

The master palette is **near-neutral, mineral, archival, and material-first**, with controlled anomalous accents.

Core family:

- **Void Charcoal** `#171816`
- **Ink** `#232522`
- **Old Bone** `#D8CEB8`
- **Paper Ash** `#B6AE9D`
- **Oxide** `#9B4335`
- **Bruised Indigo** `#39445B`
- **Tarnished Brass** `#B08B45`
- **Archive Green** `#596252`

These are production anchors, not a rule that every screen must literally contain all eight.

## Floor accents

Each Floor receives one controlled accent family driven by environment/material logic.

Floor I — THRESHOLDS should favor:
- dim mineral/stone neutrals;
- oxidized metal;
- old painted surfaces;
- cold blue/green distance;
- restrained warm threshold light.

Do not use `occult purple` as automatic weirdness.

## Anomaly color

Unnatural/high-strangeness colors should be **rare enough to mean something**.

A specific researched manifestation may retain a documented iconic color when relevant — e.g. Mustang/Blucifer's intense blue and red-eye identity — while the surrounding game art keeps it integrated rather than neon-stickered onto the scene.

---

# 7. CAMERA / COMBAT STAGING

The game uses a **2.5D illustrated stage**, not an isometric map and not a literal tabletop.

## Desktop combat layout

Reference design frame: **1440 × 900**.

- monster occupies upper-middle / right-biased visual field;
- player presence occupies lower-left or lower-middle edge without obscuring dice;
- monster locked dice read above/near the monster;
- player roll occupies the lower decision plane;
- Fight / Spoils separation happens close to the dice, not in a distant sidebar;
- margin preview sits between opposing totals.

## Mobile portrait layout

Reference design frame: **1080 × 1920**.

- monster art occupies upper 35–42%;
- enemy dice + Instinct sit directly below or integrated into the lower edge of monster art;
- player dice dominate central decision zone;
- persistent player controls / HP sit within thumb-safe lower region;
- no essential interaction requires drag precision.

The same illustrated assets should support both layouts through anchor/crop rules rather than requiring an entirely separate art set.

---

# 8. PLAYER CHARACTER SYSTEM

Recurring player characters require locked model sheets before production poses.

## Proportions

Baseline humanoid model:
- approximately **7.25–7.75 heads** tall depending on character;
- slightly enlarged hands / equipment silhouettes for mobile readability;
- head not chibi or caricatured;
- boots/feet simplified enough to survive small display sizes.

Character individuality should come from:
- body proportion;
- posture;
- clothing construction;
- tool/equipment silhouette;
- facial structure;
- material palette;
- casting habit.

Not from random accessories pasted onto the same generic body.

## Required model sheet

For every recurring player character:

- neutral front;
- neutral 3/4;
- profile;
- back;
- silhouette-only strip;
- head front / 3/4 / profile;
- hand construction;
- height scale;
- core outfit exploded callouts;
- casting kit callout;
- equipment attachment points;
- material labels;
- approved palette;
- three facial expressions;
- idle key pose;
- Fight commit pose;
- impact/hit pose;
- defeat pose.

## Consistency rule

No production pose is generated from text alone once a character model sheet exists.

Future pose generation/editing must use the approved reference image(s) and be visually checked against:
- skull shape;
- nose/chin;
- hairline;
- shoulder width;
- limb proportion;
- clothing seam placement;
- equipment location;
- palette/materials.

A beautiful wrong character is still wrong.

---

# 9. MONSTER SYSTEM

Monsters can vary dramatically but must share rendering grammar.

Each vertical-slice enemy needs:

- canonical silhouette;
- taxonomy: Residue / Convergence / Native / etc.;
- provenance notes where relevant;
- scale relative to player;
- front/3-quarter combat presentation;
- focal anatomy tied to mechanics;
- material/texture notes;
- idle key pose;
- impact reaction;
- defeat/resolution state;
- UI portrait/crop guidance.

## Sourced manifestations

Research-derived creatures/objects preserve **verified distinctive features** before stylistic interpretation.

Do not design from vague pop-culture memory.

## Original manifestations

Originals must receive the same specificity as sourced entries.

`Spooky shadow creature` is not an original monster concept.

The first native set — Latchling, Turnback, Unadmitted, Doorwake, Toll Eater, Seal-Bearer, and the First Door boss seed — should develop a recognizable **Below-native material/anatomy language** during C-stage exploration.

---

# 10. BELOW-NATIVE VISUAL LANGUAGE — INITIAL HYPOTHESIS

Natives should not simply be `occult monsters`.

Working common traits to test visually:

- anatomy shaped by **function** rather than terrestrial taxonomy;
- seams, interfaces, hinges, impressions, pressure surfaces, folds, gaps, cavities, and wrong depth;
- materials that sit between mineral, paper-fiber, keratin, painted wood, shell, and architectural finish without literally becoming household objects;
- repeated evidence that they inhabit **boundaries between states**;
- fewer recognizable occult symbols than Residues/Convergences;
- face placement not guaranteed.

Hard rejection:
- every Native covered in eyes;
- every Native has deer skull / antlers;
- black smoke + long fingers as universal shorthand;
- random sacred geometry tattooed onto skin.

Floor I should discover one or two recurring physical principles that later Natives can inherit.

---

# 11. THE FIRST DOOR — BOSS VISUAL TARGET

The preferred Floor I boss must be immediately legible as a threshold and then resist literal interpretation.

Required conceptual elements:

- freestanding structural opening with no reliable wall;
- mutually incompatible architectural/material histories occupying one coherent body;
- closures / handles / hinges that cannot all belong to the same side;
- depth inside the opening that does not agree with surrounding perspective;
- seams occupied by Below-native material rather than `monster mouth` anatomy;
- readable OPEN / CLOSED state change at mobile scale.

Avoid:
- big wooden door with teeth;
- giant eyeball in a doorway;
- obvious portal swirl;
- generic cathedral gate;
- direct collage of famous historical doors.

The boss should feel like a function that became an organism.

---

# 12. DICE — PRIMARY GAME OBJECTS

The dice are effectively recurring characters and deserve bespoke design.

## Physical appearance

- tactile, slightly worn casting lots;
- edges softened enough to look handled, not toy-soft;
- pips remain primary visual language;
- optional numeric accessibility label integrated without making dice look like app buttons;
- shallow material irregularity so rolling feels physical;
- player and enemy dice distinguishable by **shape language / border / engraving treatment**, not color alone.

## States

Every die needs unmistakable visual treatment for:

- uncommitted;
- selected for Fight;
- potential Spoils;
- enemy unlocked;
- enemy locked;
- manipulated;
- unavailable/sealed;
- persistent LOCK across rounds.

## Manipulation animation grammar

### BUMP
Value visibly steps one face / one pip state. No magical explosion.

### FLIP
Die performs a physical half-turn to its opposite face.

### COPY
Source and target receive a brief relational line/echo before target resolves.

### TRANSMUTE
Face inscription/pips structurally rewrite; avoid generic dissolve.

### LOCK
A physical/diagrammatic bracket, frame, or registration mark settles around the die. Do not use a literal padlock icon as the only signal.

---

# 13. UI SYSTEM

The UI should look like **a field instrument designed by somebody with access to both an archive and a very good graphic designer**.

## Hierarchy

### Tier 1 — decision
- dice;
- Fight total;
- Monster total;
- predicted margin;
- Spoils pair;
- HP.

### Tier 2 — rules
- Instinct;
- active Artifact/Gear effects;
- manipulation availability.

### Tier 3 — world texture
- encounter taxonomy;
- specimen metadata;
- archive marks;
- flavor lines;
- source-inspired microdetail.

Tier 3 is never allowed to obscure Tier 1.

## Decorative system

Use:
- fine ruled lines;
- measured arcs;
- registration ticks;
- specimen brackets;
- asymmetrical annotation blocks;
- occasional overprint / misregistration texture;
- restrained paper/ink artifacts.

Avoid:
- fake classified stamp spam;
- huge red `CONFIDENTIAL` graphics;
- random coordinates on every screen;
- all-seeing eyes as generic decoration.

---

# 14. TYPOGRAPHY

The production UI should use open-licensed typefaces wherever practical.

Working system to test:

## DISPLAY / LORE SERIF
**Source Serif 4** or another high-quality OFL serif with strong small-cap and text behavior.

Purpose:
- encounter names;
- codex headings;
- Floor title cards.

## UI SANS
**IBM Plex Sans / IBM Plex Sans Condensed**.

Purpose:
- combat labels;
- buttons;
- stats;
- item rules.

Its technical/institutional character supports the world without becoming a novelty typeface.

## MONO / METADATA
**IBM Plex Mono**.

Purpose:
- coordinates;
- accession-like metadata;
- debug-like details that are genuinely diegetic.

## Logo
The title logo must become custom lettering / custom lockup. Do not leave the final game logo as a font typed in all caps.

Typography must be tested on mobile before it is considered locked.

---

# 15. ENVIRONMENT SYSTEM

The environment should feel accumulated rather than procedurally random.

## Layer structure

Each combat environment should support:

1. far atmospheric plane;
2. architectural / structural midground;
3. combat footing / foreground;
4. optional motif object layer;
5. UI-safe negative-space zones.

These can be exported as separate images for restrained parallax.

## Floor I — THRESHOLDS

Visual vocabulary to explore:

- passages that have been sealed and reopened many times;
- incompatible frames nested inside one another;
- worn stone / painted institutional metal / old wood / below-native seam material;
- wayfinding marks from different eras;
- abandoned attempt(s) to standardize passage;
- light that implies another space without turning into generic glowing portal art.

The player should feel they are crossing through accumulated **methods of entry**, not walking through `haunted castle level`.

---

# 16. ANIMATION STRATEGY

The vertical slice uses **high-resolution illustrated key poses with controlled 2D rig/transform animation**, not frame-by-frame AI generation.

## Why

- preserves character identity;
- lets us hand-correct anatomy once;
- reduces asset drift;
- keeps download size sane;
- supports fast turn-based combat;
- allows impactful pose changes without requiring 30 unique painted frames per move.

## Production method

1. generate/draw approved model sheet;
2. create production key pose from approved model;
3. separate art into logical layers only where animation needs them;
4. clean transparent edges in Krita;
5. animate with transforms / mesh deformation / authored pose swaps;
6. use brief VFX for impact, not to disguise bad motion.

### Player minimum
- idle breathing / weight shift;
- Cast / roll gesture;
- commit / attack anticipation;
- attack resolution;
- hit reaction;
- defeat.

### Normal monster minimum
- idle;
- roll/settle response or pressure animation;
- attack/resolve;
- hit;
- defeat.

### Boss
- unique OPEN/CLOSED state;
- state transition;
- authored impact/recovery;
- defeat resolution.

# 17. TOOL / PIPELINE DECISIONS

## Concept + base art
- generative visual-development passes are acceptable for concept/model exploration;
- every accepted recurring design must be converted into a locked reference sheet;
- final assets require human/model QA against that sheet.

## Cleanup / paintover
**Krita** is the preferred raster master tool.

Use for:
- edge cleanup;
- paintover;
- transparent layers;
- pose corrections;
- export masters;
- limited frame animation when useful.

Krita supports PNG-sequence animation export, which keeps individual frames inspectable before packing. cite source note retained in production research; docs.krita.org Render Animation

## Vector / UI
**Inkscape** for:
- interface rules;
- brackets;
- icons;
- logo construction;
- scalable diagrams;
- non-historical original geometry.

## Runtime renderer — implementation recommendation
**PixiJS v8** is the current preferred renderer for a production browser build once implementation begins.

Reason:
- dedicated high-performance 2D rendering;
- stable WebGL path for production;
- spritesheet / atlas workflow;
- asset bundles and common web texture formats;
- enough custom rendering for dice/VFX without adopting a larger game engine before needed.

Use WebGL as production default; do not depend on WebGPU-only behavior for the vertical slice.

## Image processing
**sharp** in the asset build pipeline for deterministic:
- resize;
- crop;
- WebP/AVIF conversion;
- alpha handling;
- generated preview sizes.

## Atlas packing
Evaluate an MIT/open-source deterministic packer such as **texpacker** once runtime sprites exist.

Atlas generation must be scriptable in CI; do not make a GUI-only proprietary tool a required build step.

## Rigging
Do **not** lock the project to Spine or another paid proprietary editor during preproduction.

For the vertical slice, prefer:
- authored Pixi transform hierarchy / mesh where simple;
- pose swaps;
- limited layered character rig.

**SpriteForge** is an interesting MIT, browser-native experimental rig editor and may be evaluated, but its current early-release status means it is a tool candidate, not a production dependency.

Rive runtimes are MIT/open-source, but Rive is not currently the preferred path for painterly combat characters; it may remain useful for vector UI/motion if needed.

# 18. SOURCE / RUNTIME ASSET SPEC

## Character / normal monster source master

- working canvas: **2048 × 2048 RGBA** minimum for full-body combat plate;
- preserve at least 8% transparent safety margin around approved silhouette;
- source format: layered `.kra` plus lossless PNG proof;
- color space: sRGB;
- no baked UI background;
- keep named logical layers when rigging is intended.

## Boss source master

- up to **3072 × 3072 RGBA** for the vertical-slice hero asset if silhouette/detail needs it;
- runtime export still generated at target display sizes.

## Runtime raster exports

Generate from source, never hand-resize individual files.

Initial tiers:
- 1024px major combat asset;
- 512px compact/mobile asset where visual tests permit;
- WebP with alpha for runtime where quality is acceptable;
- lossless PNG retained for masters and any asset where WebP introduces edge artifacts.

AVIF is preferred for large static non-alpha environment plates only after decode/performance testing.

## Atlases

Initial vertical-slice target:
- maximum **2048 × 2048** per general sprite atlas where practical;
- 4–8px padding/extrusion depending on filtering;
- do not rotate asymmetric combat sprites if that complicates runtime pivots;
- separate frequently changing/effect textures from giant static environment plates.

## UI source

- vector-first SVG for original interface geometry/icons where possible;
- 24 / 32 / 48 / 64 CSS-pixel visual tests;
- raster effect masters at 2× expected largest display size.

# 19. FILE / NAMING CONVENTION

Source path pattern:

`art/source/<category>/<id>/<id>_<view-or-state>_v###.kra`

Runtime path pattern:

`public/assets/<category>/<id>/<id>_<state>@<scale>.webp`

Examples:

- `art/source/enemy/latchling/latchling_model_v003.kra`
- `public/assets/enemy/latchling/latchling_idle@1x.webp`
- `public/assets/enemy/latchling/latchling_hit@1x.webp`
- `art/source/boss/first-door/first-door_open_v002.kra`

Every researched manifestation also retains its research ID in metadata/build manifest even when the display name differs.

---

# 20. GENERATED-ASSET PROVENANCE

Each accepted generated asset should record:

- date;
- purpose;
- model/tool family if relevant to internal production tracking;
- reference-sheet version;
- source research record(s);
- subsequent paintover/edit status;
- rights/provenance notes for any external visual reference.

Do not place prompt text in player-facing metadata.

The project must be able to answer: **which approved design did this asset come from?**

---

# 21. QA GATES

An asset fails production review if any of the following are true:

- silhouette unreadable at intended mobile size;
- recurring character no longer looks like the model sheet;
- sourced manifestation contradicts verified distinctive features without deliberate fiction note;
- hands/equipment/anatomy visibly broken;
- transparent edges contain halos/jagged contamination;
- lighting direction conflicts badly with environment;
- costume details randomly appear/disappear between states;
- deep-cut visual reference is incorrect;
- copyrighted modern visual design was inadvertently copied;
- important game state depends only on color;
- decorative texture competes with the dice.

---

# 22. C-STAGE DELIVERABLE ORDER

Produce in this order:

1. **visual direction board** — original synthesis, not a collage-copy target;
2. **palette/value study**;
3. **dice design sheet** — because dice are the most repeated object;
4. **combat UI layout sheet** — desktop + mobile;
5. **first player-character model sheet**;
6. **Latchling / Doorwake / Seal-Bearer model sheets**;
7. **First Door boss visual-development sheet**;
8. **Floor I environment sheet**;
9. **animation/VFX grammar sheet**;
10. **runtime export QA test** with real assets in a browser scene.

Do not generate a batch of 20 monsters before steps 1–4 agree with each other.

---

# 23. C-STAGE SUCCESS TEST

Before D-stage content lock, put these on one screen together:

- one player character;
- one researched Residue;
- one original Native;
- one Artifact;
- four player dice;
- one enemy dice set;
- Floor I environment;
- combat UI.

If they look like they came from different games, C is not done.

If the dice become hard to read because the art is too beautiful, C has failed.

If the game looks like a conspiracy-themed skin laid over generic fantasy, C has failed.

If it looks like a coherent fantasy world whose creators know disturbingly specific things, C is working.
